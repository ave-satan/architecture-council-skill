# Подготовка реализации

Режим вызывается обычным запросом «Подготовь реализацию этой фичи», «Разбей пакет
на задачи» или «Обнови roadmap». Подготовка не запускает кодирование. Если запрос
явно включает начало реализации, после подготовки передай работу в применимый
workflow проекта в уже разрешённом scope; повторное такое же разрешение не нужно.

## Основание и декомпозиция

Определи выбранный пакет из контекста; неоднозначный выбор уточни. Прочитай его
README с решением, requirements, target architecture, delivery plan и Council Review.
Сверь с текущим кодом, правилами проекта и уже выполненной работой. Зафиксируй
architecture_revision и воспроизводимый code_revision: commit либо commit с
идентификатором снимка незакоммиченных изменений. При отсутствии Git укажи
датированный snapshot/hash релевантных входов. Не подменяй фактическую проверку
кода ссылкой на старый план.

Сохраняй существующие INC и их связи. Разбей их на задачи с ограниченным,
проверяемым результатом; техническая подготовка допустима, если имеет собственный
контракт и разблокирует полезный результат. Не дели механически по слоям, файлам
или произвольным часам. Карточка должна позволять другой сессии начать работу
по её тексту и адресным ссылкам без чтения всей переписки.

Roadmap остаётся в delivery-plan.md. Для сложной поставки группируй инкременты
в логические блоки по результату, выпуску или переходу; для простой фичи группы
не нужны. Покажи обязательные зависимости, внешние блокеры и доступные параллельные
ветки. Рекомендуемый порядок и конфликт редактирования не выдавай за обязательную
зависимость. Учитывай общие контракты и пересечение изменений перед параллельным
запуском. Не придумывай сроки или исполнителей без основания.

Зависимость разработки должна требовать конкретный готовый вход, а не всю приёмку
соседнего компонента. Если реализация и общая приёмка имеют разные входы или
блокеры, выдели их в самостоятельные проверяемые задачи; не дроби работу, которая
принимается как одно целое. Приёмка инкремента может ждать реальную среду, пока
компоненты проходят собственные контракты на разрешённом стенде. Не помещай
проверку, которая завершает задачу, только в её заблокированного потомка.

На продолжении исправляй слишком широкую декомпозицию явно: сохраняй IDs, исходный
scope и evidence в истории; выделенному остатку назначай новый ID и связи,
обновляй потребителей зависимостей. Не сужай молча критерий ради DONE. Совокупность
задач должна сохранить прежние обязательства; изменение требований возвращается
на проектирование. Незавершённость всей фичи сама по себе не отменяет DONE компонента.

Ближайшие задачи детализируй полностью. Дальние можно оставить PLANNED с явным
условием детализации, но уже назначенными требованиями и ожидаемым результатом.
Неподтверждённая архитектура допускает черновую декомпозицию; зависимые задачи
сохраняют блокер, независимые части планируются. Существенное расхождение с кодом
верни на адресное проектирование, не меняя молча требования и ADR.

## Артефакты

Скопируй только при первом вызове единый
[Implementation Plan](../assets/feature-package/implementation-plan.md) в выбранный
пакет; переведи текст на язык пакета и заполни metadata. Повторный вызов обновляет
этот файл, не перезаписывая существующую работу. Новые IDs монотонны, отменённые не
переиспользуются. Сохраняй DONE с evidence; устаревшую работу отмечай CANCELLED
с причиной и заменой. Изменение требований требует повторной проверки затронутых
задач, не автоматического сохранения READY или прежнего архитектурного approval.

delivery-plan.md содержит архитектурный roadmap и переход; implementation-plan.md —
единственный источник карточек, статусов и текущей передачи в реализацию. Для большого плана
подробности можно вынести в Markdown-файлы под implementation/, оставив в индексе
ссылки вместо копий. Их revision/language должны соответствовать пакету; старые
версии сохраняй как историческое evidence. Mermaid — inline, ссылки — кликабельные.

Не добавляй отдельные roadmap, task index или handoff и не делай карточки обязательными для обычного
архитектурного прогона. Задачи здесь — документы; задачи Codex или внешнего трекера
создаются только по отдельному запросу. Task-plan отображает текущую работу агента,
а не заменяет сохранённый план реализации фичи.

## Контракт таблицы

После `AC:IMPLEMENTATION_TASKS` идёт одна таблица с девятью колонками в порядке
шаблона: Task, Increment, Requirements, Dependencies, Status, Blocker,
Acceptance, Verification, Evidence. В Task — Markdown-ссылка с единственным
TASK-### в подписи на карточку с названием, scope и необходимыми входами.
Остальные ссылки также оформляй кликабельно; IDs извлекаются из подписей.
Dependencies — TASK IDs либо `—`. Статусы: PLANNED, READY, BLOCKED, IN_PROGRESS,
DONE, CANCELLED. Для отсутствующих blocker/evidence используй `—`.

READY означает достаточные входы, законченные зависимости и проверяемый scope,
но не авторизацию. BLOCKED требует конкретной причины; DONE — ссылки на результат
и проверки. PLANNED может зависеть от незавершённых задач. Для CANCELLED укажи
причину в Blocker; требования должны остаться покрыты действующими задачами.
У задач выполнения применимые условия разрешения проверяются по реальному запросу
и launch boundary в Implementation Plan, не выводятся из статуса таблицы. Design metadata implementation_start
не переписывается как журнал запуска: это историческая граница архитектурного режима.

## Продолжение авторизованной реализации

Этот режим сопровождает сохранённый план; кодирование следует применимым правилам
проекта. Scope берётся из фактической команды пользователя: рекомендуемый первый
инкремент в Implementation Plan не сужает запрос реализовать всю фичу. После результата и
необходимых проверок продолжай следующую доступную работу в разрешённом scope.
Сообщение о промежуточном результате не требует остановки до очередного «продолжай».
Останавливайся при завершении scope, явной остановке пользователя или когда для
дальнейшей работы действительно нужен недоступный вход, разрешение либо ресурс.
Блокер одной ветки не останавливает независимую разрешённую работу. Подготовка
без команды реализации по-прежнему заканчивается передачей плана.

Для устанавливаемого продукта запланируй раннюю проверку установки, запуска,
применимых разрешений и основного пользовательского действия, а также обновления
и повторного запуска. Выполни её при появлении минимальной рабочей сборки, до
наращивания следующих компонентов. Для другого типа продукта выбери аналогичную
проверку его реальной точки входа. При недоступном UI проверь доступную часть
runtime/сборки и укажи границу; не подменяй UI-проверку компиляцией и не передавай
пользователю действия, которые можешь выполнить в пределах разрешений.

После значимого результата сверь текущие карточки, ссылки roadmap/launch boundary и
сводку проверки с фактическим состоянием. Убирай устаревшие утверждения об отсутствии
кода, установок или разрешений; сохраняй реальные открытые условия. Уже полученные
проверки другой задачи свяжи с ней сразу, не объявляя всю задачу DONE. Карточки и
статусы остаются в индексе, история — в evidence, текущая сводка заменяется вместо
накопления хронологических абзацев. Новая сессия должна видеть оставшуюся работу
без восстановления всей переписки.

Для открытой приёмки укажи конечный набор оставшихся случаев, ожидаемый результат
и потребителя evidence. Новый существенный случай добавляй с причиной, не расширяй
проверку до бесконечного доказательства всех возможностей платформы. Безопасное
отклонение входа не доказывает поддержку обязательного сценария. В итогах называй
точно проверенный scope; не называй этап завершённым, пока его обязательные условия
открыты. Показывай следующий доступный шаг и реальную причину остановки, если она есть.

## Проверка и передача

Запусти обычный validator выбранного профиля с `--implementation-plan`; при
незавершённой архитектуре добавь `--phase draft` и явно обозначь неполную проверку.
Наличие файла также включает проверки задач в review без дополнительного флага.
Валидатор проверяет структуру, IDs, покрытие объявленных требований/инкрементов,
зависимости и циклы. Он не доказывает качество декомпозиции, истинность DONE,
безопасность параллельной работы или фактическую актуальность code_revision.

Содержательно проверь, что совокупность задач даёт обещанный результат и включает
межкомпонентную приёмку. Локальные DONE не заменяют приёмку инкремента и фичи.
Проверь применимые правила тестирования, выпуска и восстановления; не навязывай
общий checklist там, где он не нужен. Эксперименты — ограниченные задачи со сроком
и потребителем evidence, а не бессрочный барьер всей реализации.

Итог человеку: ссылка на roadmap, ближайшие задачи, что можно делать параллельно,
реальные блокеры и началась ли реализация. Подготовка не требует повторного полного
Council. При продолжении сверяй изменения кода и обновляй существующие карточки.
