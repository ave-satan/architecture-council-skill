# Контракт Architecture Package v1.5.1

Этот контракт определяет только структуру проверяемых связей. Смысл требований,
истинность evidence, реальность человеческого разрешения и качество решения
проверяются участниками Council, а не выводятся из успешного exit code.

## Язык и markers

Подготовка реализации — отдельный [режим](implementation-preparation.md).
Его implementation-plan.md необязателен для обычного дизайна. При наличии файла
review проверяет индекс задач; `--implementation-plan` дополнительно требует его
наличие. Draft/template проверяет лишь наличие требуемого файла и marker, не
готовность задач, покрытие и исполнение. Обычные проверки ссылок сохраняются.

Заголовки, обычная проза, подписи схем и человекочитаемые ячейки таблиц пишутся
на языке пользователя. Точные технические идентификаторы и термины можно
сохранить, но они не делают допустимой англоязычную связующую или описательную
фразу вокруг них. Идентификаторы полей, Role IDs и HTML-комментарии `AC:*` /
`SSC:*` сохраняются. Таблица следует после
своего marker; первая строка — локализуемый заголовок, следующая — разделитель,
затем данные в порядке колонок шаблона. Не переноси несколько таблиц под один
marker и не меняй порядок колонок. Значение `|` в ячейке экранируй `\|`.

README содержит уникальные `AC:README:summary`, `overview`, `reading`,
`documents`, `adrs`, `interpretation`, `next`, `implementation`. Перевод слов
в заголовках не изменяет эти markers.
Markers обозначают назначение частей README, а не обязательные отдельные
заголовки. README совмещает краткое текущее решение, запись ответа человека
`AC:HUMAN_REVIEW` и базовую навигацию по техническим документам. Содержание
связанных документов в нём не повторяется. Новый sectioned-пакет не содержит
`decision-brief.md`; в нетронутом старом пакете этот файл поддерживается как
legacy-источник решения до следующей содержательной ревизии.

Marker/table/metadata являются проверяемыми единицами. Отдельный файл не требуется
для каждой функции. Sectioned package объединяет classification с Charter,
verification с Delivery, решение и Human Review с README, а роли, варианты, reviews,
waivers и validation — в Council Review. Файл выделяется только из-за отдельного
жизненного цикла, большого raw evidence или внешней передачи.

## Название и номер пакета

Новые пакеты называются `001 — Синхронизация календаря`: порядковый номер и
короткое содержательное название на языке пользователя. Общий каталог проекта —
`architecture/`, либо уже принятый в проекте каталог, переданный через
`--package-root`. Не добавляй дату или технический slug в видимое имя.
Initializer сам назначает следующий номер; сохраняй его `package_number`,
`package_name` и заголовок в README, используй это имя в ссылках
и сообщениях человеку. `--slug` необязателен и служит только техническим ID.

Продолжение работы и новая архитектурная ревизия остаются в том же пакете с тем
же номером. Старые пакеты и явный позиционный путь initializer поддерживаются;
переименование существующих папок с обновлением ссылок — отдельная задача.
Ненумерованные старые папки не участвуют в счётчике новых пакетов.

Скрытый файл `.package-sequence` в общем каталоге хранит последний выданный номер
и блокирует одновременное выделение номеров. Сохраняй его при переносе или
резервном копировании каталога. Учитываются также уже существующие номера;
удалённый номер не используется повторно, пропуски после неудачного создания
допустимы. Повреждённый счётчик требует проверки, а не молчаливого сброса.

## Ревизии

Все активные корневые документы, ADR и evidence имеют `architecture_revision`,
совпадающую с README. Для старого Target допустим `revision`, но при наличии
обоих полей они обязаны совпадать. У Red Team `subject_revision` тоже совпадает.
Исторический ADR/evidence помечается `status: SUPERSEDED` (отклонённый ADR —
`REJECTED`); его revision не переписывается.

README хранит `council_recommendation`, `human_review_status`, `design_maturity`,
единственное текущее решение Council и Human Review той же revision. Implementation Plan
создаётся только при подготовке реализации и относится к той же revision.
`implementation_start` остаётся
`NOT_REQUESTED` в архитектурных документах.
Рекомендация пакета совпадает с `council_recommendation` последней Arbiter section
из Council Review той же revision. Preliminary Arbitration не заменяет итог.

## Роли и L1

Минимальные роли добавляет initializer: Intake, Domain, Solution,
Implementation/Maintainability и независимый Arbiter. Для L2–L3 добавляются
Challenger и Red Team; для brownfield L2–L3 — System Discovery; для L3 —
Security/Privacy. Дополнительные роли определяются рисками. Полный список
фиксируется одинаково в Charter metadata и Council Review. CLI `--roles`
добавляет роли к сохранённым, а не заменяет их.

L1 не обязан иметь независимый challenge, Preliminary Arbitration или Red Team.
Его Coverage — `NOT_APPLICABLE_L1`, а решение описывается в Target. Если роль
дополнительно выбрана, её output и запись запуска обязательны.

`AC:ROLE_RUNS`: Run ID, Stage, Role, Actor ID, Input revision/hash, Output,
Gate result, Started, Completed. Все поля обязательны; даты ISO-8601 с timezone.
Последний запуск выбранной роли должен завершиться `PASS`. Output — локальная
ссылка внутри пакета на непустую актуальную секцию Council Review или отдельное
evidence, оправданное объёмом либо жизненным циклом. Старые запуски сохраняются
отдельными строками; для их outputs используй архивные пути, если секция или
документ заменены. Run ID уникален.

`AC:REVIEWS` связывает role run с секцией review: Role, Run ID, Actor ID,
Input revision/hash, Section, Verdict и Findings. `AC:ROLE_COVERAGE` содержит
выбранную роль, тот же output и статус `COMPLETE`; `MISSING` не является
подтверждением выполненного review. Реальное исполнение и независимость агента
дополнительно проверяются по истории его запуска. В legacy-пакетах эквивалентом
этой записи остаются metadata отдельных review-файлов.

Для L2–L3 Council Review содержит заполненные таблицы `SSC:FAMILIES`
(6 колонок шаблона) и `AC:OPTIONS` (Option ID, описание/ссылка, feasibility).
Перед выбором кандидата нужен хотя бы один `VIABLE`. Поля
feasibility отражают достаточность evidence для проектного выбора по протоколу,
а не факт исполнения всех будущих приёмочных тестов. Валидатор не определяет
семантически, какой gap является no-go; это обосновывает арбитр. Поля
`coverage_challenger_run_id`, `coverage_challenger_actor_id`,
`coverage_input_revision` ссылаются на реальный завершённый запуск роли
`solution_space_challenger`, чей output — соответствующая секция Council Review. Если один
исполнитель также является Alternative Architect, зафиксируй оба запуска;
с Solution Architect/Arbiter/Red Team их не совмещай без разрешённого waiver.

## Трассировка

Определения требований содержат ID в Markdown-заголовках, например
`### FR-001: ...`; сценарии — `SCN-*` в Charter, инкременты — `INC-*` в Delivery.
Каждое объявленное BR/FR/QA/INV/CON/TR имеет строку `AC:TRACEABILITY`:
BR, Requirement, SCN, Architecture/ADR, INC, VER, SIG.

Requirement — один ID либо Markdown-ссылка с этим ID в подписи на его определение
в requirements.md. Пустые, неизвестные и составные ID не допускаются; ссылки и
их якоря проверяются отдельно. Architecture/ADR — ссылка на Target/активный ADR.
Голый ADR ID в старых пакетах распознаётся для совместимости, но новые и
редактируемые отсылки оформляй ссылками по правилам навигации.
`AC:VERIFICATIONS` в Delivery Plan определяет VER в первой колонке и
перечисляет проверяемые requirement IDs во второй. `AC:SIGNALS` определяет SIG
в первой колонке; он может обозначать метрику, запись журнала или доступный
пользователю проверяемый сигнал. Это не требование вводить внешнюю телеметрию.

Неприменимое звено, кроме самого Requirement, имеет формат
`N/A; reason=конкретное обоснование; owner=владелец`. Причина и владелец обязательны.
Пустая таблица не покрывает существующие требования. Не создавай фиктивные IDs
ради прохождения проверки.

## Изменения входов и классификация

После discovery или новых фактов/требований/варианта проверь hard triggers,
уровень, роли и обязательные артефакты. Обнови состав пакета по manifest.
Затем выполни `scripts/record_classification.py PACKAGE`. Он записывает digest
Charter, Requirements и Context/Dossier, а также выбранные роли. Это фиксация
выполненной проверки, не автоматическая оценка рисков. При изменении этих
документов digest становится устаревшим; перед handoff нужно повторить проверку.

## Waiver

`AC:WAIVERS` в Council Review: Waiver ID, Actor ID, полный набор совмещаемых Roles через
запятую, Revision, Approved by, Approved at, Evidence. Если отступлений нет,
таблица пустая. Evidence — локальный документ реального решения человека с
`status: APPROVED`, `architecture_revision`, `approved_by`, `approved_at`.
Он должен указывать источник разрешения. Не сочиняй его от имени пользователя.
Scope и revision точные; чужой/устаревший waiver не применяется. Валидатор выдаёт
WARNING/WAIVED. Это не доказательство независимости и не разрешение пропустить
саму работу/обязательные outputs.

## Ссылки и code evidence

Локальные Markdown-ссылки проверяются на существование пути и раздела, а
`:N`, `:N-M`, `#LN-LM` — на диапазон строк текущего файла. Удалённые ссылки
автоматически не загружаются. Для фактов о коде используй `AC:CODE_EVIDENCE`:
Claim ID, Repo-relative path, Revision, Start, End. `repository_root` указывает
доступный локальный репозиторий. Revision — полный commit SHA или
`WORKTREE:<sha256 файла>`. Проверяется ровно этот snapshot и включительный
диапазон строк. Для исследования без code claims допустима пустая таблица с
`code_evidence_status: NOT_APPLICABLE` и `code_evidence_reason` в metadata.

Mermaid находится внутри fenced-блоков `mermaid` в Markdown. Комментарии
`%% ac_id:`, `ac_state`, `ac_purpose`, `ac_scope`, `ac_legend`, `ac_revision`,
`ac_normative` задают идентичность и metadata нормативной схемы (исключение для
исследовательских иллюстраций описано ниже). `ac_id` уникален в документе;
ссылка ac_normative разрешается относительно Markdown-файла, может указывать
на него самого. Revision совпадает с текущим пакетом.

Для L2–L3 в target-architecture.md обязательны `target-container` и `key-flow`;
в brownfield в current-system.md — `current-container`. Для L1 схемы необязательны;
добавленные схемы проверяются по тем же правилам. Другие схемы добавляются по необходимости.
Если фича меняет хранимые, передаваемые, кешируемые или производные данные,
`target-architecture.md` также содержит модель затронутых данных, достаточную для
проверки полей и типов, обязательности либо допустимости `null`, ключей и уникальности, связей и
кардинальности, инвариантов и состояний, владельцев, чувствительности, срока хранения
и эволюции схемы. Изменённая модель содержит встроенную Mermaid-схему:
`erDiagram` для сущностей и кардинальности либо `classDiagram` для DTO, сообщений,
объектов-значений и моделей документов. Компактная таблица рядом фиксирует типы,
допустимость `null`, индексы, ограничения, сроки хранения и эволюцию, которые
схема не выражает точно. Обе части находятся в существующем документе и не
создают новый файл. Если модель не меняется, достаточно явной отметки и ссылки
на актуальное описание текущей модели; новая схема не требуется.
Схемы исторических ADR/evidence сверяются с revision своего документа и не
засчитываются как текущие обязательные схемы. Их metadata и ссылки сохраняются.
Валидатор проверяет наличие блоков, закрытие fences, непустое тело, IDs, metadata
и ссылки. Он не исполняет Mermaid и не доказывает корректность синтаксиса/раскладки.
Редактор пользователя с Mermaid-плагином считается доступным; отдельные render
и визуальный gate не нужны. Отсутствие SVG/PNG не создаёт warning.

Старые пакеты с diagrams/target/container-view.mmd, key-flow-sequence.mmd и
brownfield diagrams/current/container-view.mmd поддерживаются без обязательного
рендера. При изменении такой схемы перенеси её в связанный Markdown с ac_id и
обнови ссылки; не сохраняй две активные копии одной схемы. Старый флаг
--allow-missing-render оставлен для совместимости команд и ссылок старых пакетов.

## Готовность пакета

Council Review хранит завершённые запуски ролей, reviews, gates и результат
валидации. Текущее состояние revision задают README, Council Review и
`evidence/revision-impact.md` при пересмотре. Отдельной временной шкалы процесса нет.

Для обычной review-проверки Council Review обязан иметь
`package_validation_status: PASS`, текущую `architecture_revision` и заполненную
таблицу `AC:PACKAGE_VALIDATION`. Первый полный прогон выполняется с
`--validation-candidate`; он проверяет будущий PASS без циклической зависимости,
но не означает готовность к handoff. После успешного кандидата обнови секцию
валидации Council Review и повтори обычную review-проверку.

## Продолжение прогона

После новых evidence или разрешения продолжить сначала выполни recovery preflight:

1. Сверь публичный корень, README, Council Review, текущий validation result и рабочую
   папку. PASS с другой `architecture_revision` недействителен.
2. Зафиксируй base revision, target revision, изменившиеся требования/evidence,
   затронутые документы, роли и gates в `evidence/revision-impact.md` рабочей копии.
3. Продолжи существующий черновик, если его происхождение и изменения доказуемы;
   иначе сохрани его как recovery evidence и начни рабочую копию от последней
   цельной revision. Не исправляй смешанный корень глобальной заменой строк.

Новые разрешения фиксируй в соответствующем decision/evidence и не трактуй
продолжение как новое approval. До promotion публичный путь остаётся на последней
цельной revision. Следующую revision собирай в скрытой соседней рабочей папке
`.architecture-council-work/<package-name>/<revision>/` на том же файловом томе.
Рабочая копия имеет явный `status: IN_PROGRESS` в `evidence/revision-impact.md`.
При паузе/прерывании оставляй этот статус, точный путь и незакрытые gates; при
отказе ставь `status: ABORTED`. Побочный вопрос пользователя не является ни
паузой, ни отменой активной revision.

Сначала обнови Charter, Requirements, секцию Classification, выбранные роли и gates.
После этого установи в impact record `intake_status: FROZEN`; до этого разрешены
только `system_discovery` и `intake_requirements`, остальные specialist runs
запрещены.

Веди последующие роли по тому же AC:ROLE_RUNS/AC:ROLE_COVERAGE контракту с новыми
run IDs. Повторно запускай только роли, чьи входы или выводы отмечены затронутыми;
неизменённое evidence переиспользуется только по точной revision/hash и с явным
обоснованием в impact record. Незавершённая рабочая revision имеет структурный
Council Review с точными входами и outputs. До promotion проверь именно рабочую папку
с `--validation-candidate`, зафиксируй PASS в его validation section, затем
повтори полную `--phase review` проверку. Одним ограниченным переключением замени публичный пакет,
сохранив восстановимую резервную копию до повторной проверки публичного пути.
Проверка старого корня не проверяет рабочую revision.

Promotion запрещён, если validation относится к base revision, intake freeze
отсутствует, есть незавершённые затронутые роли/gates или документы расходятся по
revision. После переключения повторно запусти validator по публичному пути; лишь
затем удаляй временную резервную копию.

`--phase review` по умолчанию проверяет полный пакет. `--phase draft` и
`--template-mode` не означают готовность к handoff. Неполный BLOCKED-пакет можно
передать для адресного решения человека с перечнем непройденных gates; не выдавай
успех проверки черновика за успешный Council.

## Переходы между документами

Все отсылки к другим документам пакета в тексте, таблицах, README, ADR и evidence
оформляются относительными Markdown-ссылками с понятными подписями: например,
`[требования](../requirements.md)` из evidence. Путь считается от текущего файла.
Для конкретного требования, finding или раздела используй существующий якорь;
при необходимости добавь стабильный явный HTML-якорь. Имена файлов в backticks
и голые ID не заменяют ссылки. Ссылки на отсутствующие необязательные документы
не создавай: укажи неприменимость. При переименовании обновляй входящие ссылки.

Машинные поля frontmatter, код и metadata Mermaid сохраняют свой синтаксис;
кликабельная навигация размещается в Markdown вокруг них.
Валидатор проверяет существование ссылок и якорей; полноту смысловых отсылок
проверяет агент при чтении документов.

## Исследовательские схемы и результаты проверки

По умолчанию Mermaid-схема нормативная и сохраняет полный набор ac_* полей.
Иллюстрацию гипотезы в evidence можно явно отметить `%% ac_kind: research` внутри
блока: она не требует нормативных metadata, не объявляет ac_id/ac_normative и не
заменяет обязательную схему Target или Current System. Закрытость блока и наличие
содержимого проверяются в обоих случаях. Синтаксис Mermaid и визуальный результат
этот структурный валидатор не доказывает. У самой заметки сохраняются обязательные
architecture_revision и artifact_language. Переклассификация нормативной схемы
ради обхода проверки запрещена.

CLI различает [ERROR][STRUCTURE], [ERROR][GATE] и [WARN]. Незакрытый gate по-прежнему
даёт ненулевой exit code в review; draft не проверяет готовность. Несогласованные
или неполные записи ролей остаются структурными ошибками. Legacy warning не
